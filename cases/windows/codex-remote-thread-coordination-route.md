# Codex 远程原生任务读取失败：核对入口并复用已授权协调路径

本文仅提供脱敏后的解决方案，不包含原始日志、设备信息或事件时间线。适用于远程电脑可见，但某个入口无法读取原生任务的排查场景；不是官方接口保证，也不适用于绕过权限限制。

## 1. 先区分“电脑可见”和“任务可读”

以下状态需要分别验证：

- 远程电脑在线、已连接或已附加。
- 当前入口能够列出电脑或项目。
- 当前入口支持目标原生任务的读取。
- 当前入口支持向该任务发送消息。
- 消息被接收后，目标任务确实执行并返回结果。

前两项成立，不能推出后三项成立。直接读取出现 `environment_not_found`、`DesktopThreadReadUnavailableError`，或发送出现 `CloudThreadNotFoundError`，只能说明该次调用没有成功；单凭错误名称不足以判定代理、网络或目标电脑故障。

## 2. 优先核对历史成功路径和当前能力

1. 查找以前成功读取同类任务时使用的入口，区分直接连接器与桌面原生任务接口。
2. 在当前会话中检查实际提供的工具、参数和权限。历史上存在的工具不代表现在仍可用。
3. 核对执行端身份，确认操作的是用户授权的控制端，且具备当前目标的访问权限。
4. 优先复用已存在、已获授权的协调任务，不要仅因直接入口失败就反复新建任务、重连或叠加代理设置。

常见的两条路径可以概括为：

```text
直接入口：
发起端 → 通用任务连接器 → 远程原生任务

已验证可用的协调路径：
发起端 → 已授权的现有协调任务
       → 桌面原生任务列表 → 按返回的主机与任务标识读取目标
```

两条路径使用的接口和支持范围可能不同。协调路径只有在当前工具支持、目标访问权限有效且操作已获用户授权时才可使用。若收到权限拒绝，应停止相关操作并请求正确授权，不能改走其他电脑、文件或网络路径规避拒绝。

## 3. 用最新列表结果完成最小只读验证

在已授权的协调任务中：

1. 确认当前原生接口确实提供任务列表和读取能力。
2. 获取一次最新任务列表，检查目标条目、所属主机以及不可用主机信息。
3. 从本次返回结果中取出任务与主机标识。不要猜测标识，也不要混用历史环境标识、显示名称和其他入口的标识。
4. 按当前工具定义传入参数，先只读取目标原生任务。
5. 检查返回内容是否属于所选目标，并确认它不是协调任务自身的转述或旧缓存。
6. 如果还有另一个已获授权的目标，可独立复测；不要用一个目标成功代替全部目标验证。

原生接口可能以 `list_threads`、`read_thread`、`send_message_to_thread` 等名称提供；通用连接器可能使用另一套入口。实际能力与参数以当前工具清单为准。

读取成功后，先报告“目标原生任务已可读取”。若用户还要求发送或执行，应核对该操作是否已在用户授权范围内；缺少授权时再询问。随后进行最小必要测试，并读取目标端结果验收。

## 4. 分层记录验证结果

| 验证项 | 可以得出的结论 | 不能顺带声称 |
| --- | --- | --- |
| 发起端消息被协调任务接收，协调任务完成读取 | 发起端到协调任务的消息路径可用；该次读取成功 | 已向远程目标发送执行指令 |
| 原生列表返回目标和当前主机标识 | 此次列表可发现目标 | 目标一定可读、可写 |
| 使用当前列表返回的标识成功读取原生任务 | 该路径对该目标的读取已验证 | 原先失败的直接入口已修复 |
| 两台远程电脑的目标分别读取成功 | 两个所测目标的读取均通过 | 所有电脑、所有任务均可用 |
| 目标发送接口返回成功 | 以返回语义为准，可能仅代表接收或排队 | 目标已执行、执行成功 |
| 读取到目标执行后的对应结果 | 对应操作的结果可以验收 | 后续所有操作都会成功 |

本方案对应的验证范围是：协调路径成功读取了不同远程电脑上的原生任务。当前远程目标的发送与执行没有一并验证，不能写成“远程读写全部恢复”。

## 5. 代理检查属于另一层，不要混为修复结论

Windows 进程代理可参考独立案例：[ProxiFyre 与 Clash TLS 嗅探方案](./codex-desktop-proxifyre-clash-solution.md)。仅在证据指向网络或进程接管问题时按该层排查。

需要特别注意：

- 应用匹配规则要核对实际可执行文件。名称中的 `OpenAI` 末尾是大写字母 `I`，不要把截图或 OCR 识别出的 `OpenAl`（小写字母 `l`）直接写入规则。
- 配置有效、服务运行、规则已应用，都不能单独证明目标应用流量已经被接管。
- SOCKS 端口 TCP 可连接，加上显式代理请求收到 HTTP 403 挑战响应，只能支持该次 SOCKS/TLS/HTTP 路径的有限可达性结论；不能证明进程接管、认证、WebSocket 或原生任务读取正常。
- Clash 中相关域名出现经代理的双向流量，不能单独确认准确来源进程，也不能证明应用握手成功。
- 嗅探设置应检查最终生效配置；编辑器中的片段不等于实际运行配置。
- 修正应用名称拼写、重启代理后仍无法通过直接入口读取时，应回到入口能力和路由验证，不要把这些调整写成已解决任务读取。

## 6. 最短复用清单

- [ ] 明确失败的是哪个入口、哪项能力。
- [ ] 找到历史成功路径，并核对当前工具与权限。
- [ ] 确认控制端身份、目标访问权限和用户授权范围。
- [ ] 复用现有已授权协调任务，获取最新原生任务列表。
- [ ] 使用本次返回的任务和主机标识，先做最小只读验证。
- [ ] 将发现、读取、发送、接收、执行结果分别验收。
- [ ] 权限拒绝立即停止，不用替代路径规避。
- [ ] 没有证据指向网络时，不继续堆叠代理改动。
